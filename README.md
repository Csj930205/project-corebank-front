# project-corebank-front

[![CI](https://github.com/Csj930205/project-corebank-front/actions/workflows/ci.yml/badge.svg)](https://github.com/Csj930205/project-corebank-front/actions/workflows/ci.yml)

[project-corebank](https://github.com/Csj930205/project-corebank) 코어뱅킹 API를 쓰는 화면입니다. 로그인은 하나이고, 들어온 계정에 따라 화면이 나뉩니다.

- **관리자**(창구 직원): 운영 콘솔. 아무 계좌나 열고 입출금·이체·해지를 처리하고, 전체 현황, 일 마감 결과, 감사 기록을 확인하고, 잘못된 거래를 정정(다른 관리자 승인)하고, 잠긴 로그인을 풉니다.
- **고객**: 회원가입 뒤 내 계좌 목록, 본인 명의 계좌 개설, 내 계좌의 입출금·이체·해지.

| 영역 | 선택 |
|---|---|
| 화면 | React 19, TypeScript 7, react-router 8 |
| 서버 데이터 | TanStack Query 5 |
| 빌드·개발 서버 | Vite 8 |
| 테스트·린트 | Vitest 5 + Testing Library, oxlint |

## 실행

코어뱅킹 서버(8080)가 먼저 떠 있어야 합니다.

```bash
# 1. 코어뱅킹 서버 (project-corebank 폴더에서)
colima start && docker compose up -d --wait
./gradlew bootRun

# 2. 화면 (이 폴더에서)
npm install
npm run dev          # http://localhost:5173
```

개발 서버가 `/api/*` 요청을 `http://localhost:8080/*`로 넘깁니다(`vite.config.ts`). 브라우저 입장에서는 같은 출처로 보내는 요청이라 코어 서버에 CORS 설정이 필요 없습니다. 다른 주소의 코어 서버를 쓰려면 `COREBANK_API_URL=http://... npm run dev`.

| 명령 | 내용 |
|---|---|
| `npm run dev` | 개발 서버 |
| `npm test` | 단위·컴포넌트 테스트 (vitest, 서버 없이 실행) |
| `npm run lint` | 린트 (oxlint) |
| `npm run build` | 타입 검사 + 배포용 빌드 (`dist/`) |

push·PR 마다 GitHub Actions 가 lint, 테스트, 빌드를 돌립니다(`.github/workflows/ci.yml`).

## 화면

상단 바의 메뉴(로고 오른쪽)는 로그인 상태에 따라 달라집니다. 관리자는 계좌 조회·개설(`/`), 전체 계좌(`/admin`), 일 마감, 상품·이자, 거래 정정, 감사 로그, 로그인 잠금, 관리자 계정, 고객은 내 계좌가 보이고, 로그인 전에는 메뉴 없이 오른쪽 위에 로그인·회원가입이 있습니다. 지금 화면의 메뉴가 강조되고(계좌 상세는 관리자 "계좌 조회·개설", 고객 "내 계좌"), 왼쪽 위 Corebank 로고는 관리자 `/`, 고객 `/my`, 로그인 전 `/login` 으로 갑니다. 휴대폰 폭에서는 사용자 이름을 숨기고 메뉴만 옆으로 밀어 봅니다. 메뉴를 숨기는 것은 편의이고, 실제 보호는 RequireAuth 와 서버가 합니다.

| 주소 | 누가 | 기능 |
|---|---|---|
| `/login` | 누구나 | 로그인. 관리자 계정이면 관리자 화면, 고객이면 내 계좌로 간다. 로그인 전에 보려던 화면이 있으면 그리로 돌아간다 |
| `/signup` | 누구나 | 고객 가입. 가입하면 바로 로그인되어 내 계좌로 간다 |
| `/my` | 고객 | 내 계좌 목록과 잔액 합계, 새 계좌 열기(본인 명의, 예금 상품 선택) |
| `/accounts/:id` | 관리자, 고객 | 계좌 정보와 잔액, 거래내역(더보기), 입금·출금·이체(받는 계좌번호 → 받는 분 확인 → 이체), 계좌 해지. 멱등성 시연 탭은 관리자만. 고객이 남의 계좌를 열면 "계좌를 찾을 수 없습니다" |
| `/` | 관리자 | 운영 콘솔 첫 화면. 계좌 개설(예금주 이름 입력), id로 계좌 조회, 최근 연 계좌 |
| `/admin` | 관리자 | 요약 카드, 원장 점검 결과, 계좌 목록 검색(검색어, 상태, 개설일·잔액 범위) |
| `/admin/closings` | 관리자 | 일 마감. 영업일을 골라 마감 실행, 마감 기록 목록 |
| `/admin/closings/:id` | 관리자 | 마감 결과. 요약, 일계표, 불일치 내역, 같은 날 다시 마감 |
| `/admin/products` | 관리자 | 예금 상품 목록·등록·판매 중지(두 번 눌러 확정), 이자 적립(날짜)·결산(달) 수동 실행과 결과, 최근 이자 지급 |
| `/admin/corrections` | 관리자 | 거래 정정. 거래 번호와 사유로 요청, 승인 대기·승인·반려 목록, 다른 관리자의 요청을 승인(바뀌는 잔액 확인 후 확정)·반려(사유 필수) |
| `/admin/admins` | 관리자 | 관리자 계정 목록과 등록. 정정 승인에 두 번째 관리자가 필요하다 |
| `/admin/audit-logs` | 관리자 | 감사 기록. 아이디·계좌·작업·결과·기간으로 검색 |
| `/admin/login-locks` | 관리자 | 로그인 잠금. 잠긴 아이디 목록에서 해제, 아이디를 직접 넣어 해제 |
| `/logout` | | 로그아웃. 받아 둔 데이터를 모두 버리고 로그인 화면으로 |

로그인하지 않았으면 로그인 화면으로, 고객이 관리자 주소를 열면 내 계좌로 보냅니다(`RequireAuth`). 화면에서 막는 것은 편의이고 실제 권한 확인은 코어 서버가 합니다. 예전 주소 `/admin/login` 은 `/login` 으로 넘어갑니다.

관리자 계정은 코어 서버 `.env` 의 `ADMIN_USERNAME` / `ADMIN_PASSWORD` 입니다. 고객 계정은 `/signup` 에서 만듭니다.

## 구조

```
src/
  api/          코어 API 호출. 화면 코드는 fetch 를 직접 쓰지 않고 여기 함수만 쓴다.
    client.ts       공통 요청 함수, 에러 구분(ApiError / NetworkError)
    corebank.ts     API 목록 (계좌, 내 계좌 목록, 입출금, 수취인 조회, 이체, 해지, 거래내역)
    auth.ts         로그인(관리자·고객 공용), 고객 가입
    admin.ts        관리자 API (요약, 계좌 검색, 일 마감, 상품·이자, 거래 정정, 관리자 계정, 감사 로그, 로그인 잠금)
    idempotency.ts  멱등성 키 관리 규칙
    types.ts        서버 응답 타입 (서버 Java record 와 필드 이름이 같다)
  hooks/
    useIdempotentMutation.ts  돈이 움직이는 요청용
    useSession.ts             로그인 상태(역할 ADMIN / CUSTOMER 포함)
  components/   입출금·이체·해지 폼, 멱등성 시연, 거래내역 목록, 안내 메시지,
                RequireAuth / RequireAdmin / RequireCustomer(역할별 화면 보호), MainNav(상단 바 안 역할별 메뉴)
  pages/        LoginPage, SignUpPage, MyAccountsPage, HomePage, AccountPage, AdminPage,
                ClosingsPage, ClosingDetailPage, ProductsPage, CorrectionsPage, AdminUsersPage, AuditLogsPage, LoginLocksPage, LogoutPage
  lib/          금액·날짜 형식, 에러 문장, 최근 계좌, 로그인 상태 저장, 로그인 뒤 갈 곳(landing.ts),
                일 마감 이름표·계산(closing.ts), 감사 로그 이름표·조회 조건(audit.ts), 잠금 남은 시간(loginLocks.ts),
                계좌 검색 조건(accountSearch.ts), 역할별 메뉴(nav.ts), 거래 정정 이름표·결정 가능 여부(corrections.ts), 금리 표시·입력 검사(interest.ts)
```

- 서버 데이터는 TanStack Query 로 관리합니다. 입금·출금·이체·해지가 성공하면 관련 계좌와 거래내역을 다시 불러옵니다.
- 거래내역은 서버의 커서 방식(`nextBefore`)을 `useInfiniteQuery` 로 그대로 씁니다.

## 로그인

- 관리자와 고객이 같은 로그인 화면과 같은 API(`POST /auth/login`)를 씁니다. 서버가 아이디를 보고 관리자 또는 고객 토큰을 주고, 응답의 `role` 로 갈 화면을 정합니다. 고객이 관리자 화면에서 로그인 화면으로 넘어왔으면 관리자 화면 대신 내 계좌로 보냅니다.
- 로그인하면 코어 서버가 준 JWT(30분)와 역할을 `sessionStorage` 에 둡니다. 새로 고침해도 유지되고 탭을 닫으면 지워집니다.
- 로그인 상태면 모든 API 요청에 `Authorization: Bearer` 헤더를 붙입니다. 로그인·가입 요청에는 이전 토큰을 보내지 않습니다. 토큰이 만료됐거나 401 을 받으면 로그인 상태를 지우고 로그인 화면으로 보냅니다.
- 로그아웃하면 받아 둔 데이터(계좌, 거래내역)를 모두 버려, 같은 탭에서 다른 사람이 로그인해도 이전 사용자의 정보가 보이지 않습니다.
- 같은 아이디로 5번 연속 틀리면 서버가 15분 동안 잠급니다(429 `LOGIN_LOCKED`). 수취인 조회도 고객당 시간당 30번까지입니다(429 `RATE_LIMITED`). 이 두 경우는 "N분 뒤에 다시 시도하세요" 가 담긴 서버 문장을 그대로 보여 줍니다.

## 관리자 화면

- 요약 카드는 계좌 수, 총 잔액, 거래 수와 원장 점검 결과(차변−대변, 이체 가계정 잔액, 잔액 불일치 계좌 수)를 보여 줍니다. 셋 다 0이면 "정상"입니다.
- 계좌 목록은 계좌번호 앞자리 또는 예금주 이름으로 검색하고 상태(정상/해지), 개설일 범위, 잔액 범위(원, 쉼표 허용)로 거릅니다. 범위는 양 끝을 포함하고, 시작이 끝보다 크거나 잔액이 숫자가 아니면 요청하지 않고 바로 알려 줍니다. 검색 조건과 쪽 번호는 주소(`?query=&status=&openedFrom=&openedTo=&minBalance=&maxBalance=&page=`)에 담겨 새로 고침·뒤로 가기에도 유지됩니다.
- 총 잔액은 long 범위를 넘을 수 있어 서버가 문자열로 보내고, 화면은 number 대신 BigInt 로 바꿔 천 단위 구분을 넣어 표시합니다.

## 일 마감 화면

관리자 화면의 "일 마감" 탭에서 코어 서버의 일 마감 대사 배치를 실행하고 결과를 봅니다.

- 영업일은 어제가 기본값이고, 오늘 이후는 고를 수 없습니다(서버도 422 로 거부). 날짜는 브라우저 시각 기준으로 계산합니다. `toISOString()` 은 UTC 라 한국 시각 0~9시에 하루 어긋나 쓰지 않습니다.
- 서버가 배치를 끝까지 돌린 뒤 응답하므로, 실행하면 기다렸다가 바로 결과 화면으로 넘어갑니다. 마감은 돈을 움직이지 않고 같은 날을 다시 실행해도 되어 멱등성 키는 쓰지 않습니다. 대신 연타로 두 번 실행되지 않게 막습니다.
- 결과 화면은 상태(정상 / 불일치 / 실패), 대사한 계좌 수, 마감 시점 예금 잔액, 일계표, 불일치 내역을 보여 줍니다. 계좌 불일치는 해당 계좌 화면으로 연결되고, 실패한 마감은 원인 메시지를 보여 줍니다.
- 불일치를 고친 뒤 결과 화면의 "다시 마감" 으로 같은 날을 바로 다시 확인할 수 있습니다. 이전 기록은 그대로 남습니다.
- 금액(예금 잔액, 일계표, 불일치 값)은 서버가 문자열로 보내고 BigInt 로 표시해, 2^53 을 넘어도 정확합니다.

## 감사 로그 화면

관리자 화면의 "감사 로그" 탭에서 코어 서버가 API 요청마다 남긴 기록을 봅니다. 누가(관리자·고객·토큰 없음), 언제, 무엇을, 어느 계좌에 했는지와 결과(성공 / 거부 / 실패, 에러 코드)를 최신순으로 보여 줍니다.

- 조회 조건과 쪽 번호는 주소(`?accountId=7&outcome=DENIED`)에 담습니다. 다른 관리자에게 링크로 "이 계좌의 기록" 을 그대로 넘길 수 있고, 뒤로 가기도 됩니다. 서버가 거부할 값(없는 작업 이름 등)은 주소에 있어도 버립니다.
- 거부(401/403, 횟수 제한 429)는 빨강, 업무 실패(잔액 부족 등)는 노랑으로 구분합니다. 막힌 시도가 보안상 먼저 봐야 할 기록이라서입니다.
- 요청 번호(`X-Request-Id`)를 함께 보여 줍니다. 고객 문의의 응답 헤더 값과 맞춰 그 요청을 찾을 수 있습니다.
- 이 화면을 연 것도 서버에 기록됩니다.

## 예금 상품·이자

- 계좌를 열 때(관리자 첫 화면, 고객 내 계좌) 판매 중인 예금 상품을 고릅니다. 고르지 않으면 기본 상품입니다.
- 계좌 화면 위쪽에 상품 이름과 금리가, 아래 "이자" 카드에 어제까지 쌓였지만 아직 받지 않은 **예상 이자**(세전·세금·세후)와 받은 이자 내역이 보입니다. 거래내역에는 세후 금액이 "이자" 로 들어옵니다.
- 관리자 "상품·이자" 탭: 상품 등록(금리는 0~20%, 소수 둘째 자리까지. 셋째 자리는 잘라 보내지 않고 막습니다), 판매 중지, 이자 적립·결산 수동 실행. 평소에는 서버가 매일 00:20 적립, 매달 1일 00:30 결산을 자동으로 돌립니다. 결산 결과에 실패한 계좌가 있으면 빨간 안내로 보여 줍니다.
- 일계표에 "이자" 줄이 함께 집계됩니다.

## 거래 정정 화면

관리자 화면의 "거래 정정" 탭입니다. 잘못 들어간 거래(금액 오입력, 착오 송금 등)를 원장을 고치지 않고 반대 거래(역분개)로 되돌립니다.

- 계좌 화면 거래내역에서 관리자에게는 줄마다 거래 번호와 **정정 요청** 링크가 보입니다(입금·출금·이체만. 해지 지급과 정정 거래는 되돌릴 수 없어 링크가 없습니다). 누르면 이 화면의 거래 번호 칸이 채워지고, 사유를 적어 요청합니다.
- 요청만으로는 잔액이 바뀌지 않습니다. **요청한 사람이 아닌 다른 관리자**가 승인해야 반영됩니다. 본인이 올린 요청에는 승인·반려 버튼 대신 안내가 보입니다(서버도 403 으로 막습니다).
- 승인은 "승인" → 바뀌는 잔액 안내("○○ 잔액에서 90,000원을 뺍니다") → "승인 확정" 두 번 눌러야 요청합니다. 반려는 사유를 적어야 확정할 수 있습니다.
- 다른 관리자가 먼저 결정했으면 "이미 승인 또는 반려했습니다" 를 보여 주고 목록을 새로 읽습니다. 고객이 이미 돈을 써서 잔액이 모자라면 승인이 거부되고 요청은 대기로 남습니다.
- 승인 뒤 거래내역에는 "거래 정정 · #원래거래 취소" 줄이 생기고, 일 마감 일계표에도 정정(차감)·정정(환입)이 따로 집계됩니다.
- 승인자가 필요하므로 "관리자 계정" 탭에서 관리자를 등록할 수 있습니다(아이디는 고객과 같은 규칙, 비밀번호 12자 이상).

## 로그인 잠금 화면

관리자 화면의 "로그인 잠금" 탭입니다. 고객이 "로그인이 잠겼다" 고 하면 본인 확인을 한 뒤 15분을 기다리지 않고 바로 풉니다.

- 지금 잠긴 아이디를 곧 풀리는 순서로 보여 줍니다(실패 수, 풀리는 시각, 남은 시간). 잠금은 저절로 풀리므로 목록을 30초마다 다시 읽습니다.
- 해제는 되돌릴 수 없어 "해제" → "해제 확정" 두 번 눌러야 요청합니다. 풀면 실패 횟수도 지워져 처음부터 다시 셉니다.
- 줄마다 "로그인 기록" 링크가 감사 로그(그 아이디의 로그인 시도)로 이어집니다. 본인 실수인지 공격인지 보고 판단합니다.
- 가입하지 않은 아이디도 목록에 나옵니다. 잠기는지로 계정이 있는지 알아낼 수 없도록 서버가 모든 아이디를 똑같이 잠그기 때문입니다.
- 목록에 아직 없는(방금 잠긴) 아이디는 아래 "아이디로 해제" 에 직접 넣어 풉니다.

## 중복 요청 방지

서버의 `Idempotency-Key` 규칙과 짝을 이룹니다.

| 상황 | 화면 동작 |
|---|---|
| 버튼 연타, Enter 연타 | 처리 중에는 버튼을 잠그고 추가 제출을 무시 |
| 네트워크 오류, 5xx (처리됐는지 모름) | 키를 유지. "다시 시도"하면 같은 키로 보내 서버가 처음 결과를 돌려줌 |
| 성공, 4xx (처리 안 된 것이 확실) | 키를 버림. 다음 요청은 새 키 |
| 재시도 전에 금액 등 내용 변경 | 새 요청이므로 새 키 |
| 서버가 `Idempotent-Replayed: true` 로 응답 | "이미 처리된 요청이라 처음 결과를 다시 받았습니다" 안내 |

"해지" 탭은 되돌릴 수 없는 동작이라 "계좌 해지" → "해지 확정" 두 번 눌러야 요청을 보냅니다. 해지도 남은 잔액이 나가는 요청이라 위 규칙을 그대로 따릅니다. 결과를 모르는 실패 뒤 다시 시도하면 같은 키로 보내므로 잔액이 두 번 지급되지 않습니다. 해지된 계좌의 거래내역에는 "해지 잔액 지급"으로 표시됩니다.

**이체는 받는 분을 먼저 확인합니다.** 받는 계좌번호(하이픈 있어도 됨)를 넣고 "받는 분 확인"을 누르면 서버의 수취인 조회로 가린 예금주 이름(홍*동)을 보여 주고, 그 뒤에야 "이체" 버튼이 켜집니다. 계좌번호를 한 글자라도 바꾸면 다시 확인해야 합니다. 형식이 틀리거나 내 계좌번호면 서버에 묻지 않고 바로 알려 줍니다.

"멱등성 시연" 탭은 같은 키로 1,000원 입금을 동시에 2번 보내, 두 요청이 같은 거래 번호를 받고 잔액은 한 번만 느는 것을 보여 줍니다.

## 테스트

```bash
npm test     # 112개. 서버 없이 fetch 를 가짜로 바꿔 실행한다
```

- 버튼·Enter 연타에도 요청이 한 번만 나가는지, 결과를 모르는 실패 뒤 재시도가 같은 멱등성 키를 쓰는지
- 해지가 두 번 눌러야 실행되고, 취소하면 요청이 나가지 않는지
- 이체: 받는 분을 확인하기 전에는 이체할 수 없고, 확인 뒤 계좌번호를 바꾸면 다시 확인해야 하는지
- 로그인 상태면 모든 요청에 토큰이 붙고, 401 을 받으면 로그인 상태가 지워지는지
- 같은 로그인 화면에서 관리자는 관리자 화면으로, 고객은 내 계좌로 가는지. 고객이 관리자 주소를 열면 내 계좌로 보내는지
- 일 마감: 어제 기본값, 큰 금액(2^53 초과) 표시, 불일치·실패 결과 표시
- 로그인이 잠기거나 수취인 조회 한도를 넘으면(429) 서버가 알려 준 대기 시간을 그대로 보여 주는지
- 로그인 잠금: 목록 표시, 두 번 눌러야 해제되고 취소하면 요청하지 않는지, 풀면 목록에서 빠지는지, 남은 시간 계산
- 감사 로그: 결과·에러 코드·요청 번호 표시, 주소의 조건으로 조회하고 입력란을 채우는지, 검색하면 첫 쪽부터 다시 조회하는지
- 계좌 검색: 개설일·잔액 범위가 주소와 요청에 담기는지(쉼표 제거, 상태 유지), 주소로 입력란을 채우는지, 거꾸로 된 범위·잘못된 잔액은 요청하지 않는지, 초기화
- 상품·이자: 금리 입력 규칙, 판매 중지 두 번 확인, 기본 상품은 중지 버튼 없음, 예상 이자·지급 내역 표시, 지난달 계산
- 거래 정정: 본인 요청에는 결정 버튼이 없는지, 승인은 바뀌는 잔액을 보여 준 뒤 확정해야 요청하는지, 반려는 사유가 있어야 하는지, 거래내역에서 넘어오면 거래 번호가 채워지는지
- 상단 메뉴: 역할별 메뉴, 지금 화면 강조, 로그아웃하면 메뉴가 바로 사라지는지
- 날짜 계산이 UTC 로 바뀌어 하루 어긋나지 않는지

## 한계

- 계좌 검색은 관리자 화면에만 있습니다. 첫 화면에서는 계좌를 id로 열고, 최근 연 계좌는 이 브라우저(localStorage)에만 남습니다.
- 계좌 잔액과 거래 금액은 JS number 라 2^53(약 9천조 원)을 넘으면 정확히 표시되지 않습니다(서버가 long 으로 보냄). 합계 금액(관리자 요약, 일 마감)은 문자열 + BigInt 라 정확합니다.
- `npm run build` 결과를 배포할 때는 `/api` 를 코어 서버로 넘기는 프록시(nginx 등)나 코어 서버의 CORS 설정이 필요합니다.
